# Architecture: Output Display Enhancements

## Status

Proposed

## Context

Feature 086 introduces two display improvements to tfplan2md markdown reports:

1. **Collapsible Debug Section**: Wrap the debug section in a `<details>` block (collapsed by default) to reduce visual clutter while keeping debug information accessible
2. **No-Changes Summary**: When a plan has zero resource changes, display "No changes" in the Summary section instead of an empty table, and omit the Resource Changes section entirely

These enhancements improve report readability and professionalism, especially in PR reviews where many modules may have no changes.

### Current Behavior

**Debug Section:**
- Debug output is generated by `DiagnosticContext.GenerateMarkdownSection()` in `src/Oocx.TfPlan2Md/Diagnostics/DiagnosticContext.cs` (line 194)
- The markdown is appended to the rendered output in `ProgramEntry.cs` (line 131) after template rendering completes
- Output format: `## Debug Information` heading with subsections for Principal Mapping and Template Resolution
- All debug content is visible by default

**No-Changes Summary:**
- Summary table is rendered by `_summary.sbn` template using the `summary` model
- `summary.total` (from `SummaryModel.Total` property) contains the count of resource changes (excluding no-ops)
- The summary table is always rendered with counts, even when all counts are zero
- `default.sbn` template checks `module_changes.size == 0` to display "No changes" in the Resource Changes section, but this is separate from the summary table

### Architectural Patterns

**Template-Based Rendering:**
- tfplan2md uses Scriban templates for all markdown generation
- Core templates in `src/Oocx.TfPlan2Md/MarkdownGeneration/Templates/`
- Templates use the `include` directive to compose sections (`_header.sbn`, `_summary.sbn`, etc.)

**Diagnostic Context (Optional):**
- Only created when `--debug` flag is enabled
- Components check for null before recording diagnostics (no performance impact when disabled)
- Debug output is appended after template rendering (not part of template model)

**Report Style Guide:**
- `docs/report-style-guide.md` defines formatting standards for all markdown output
- Collapsible sections use `<details>` with `<summary>` tags
- Non-breaking space (`\u00A0`) between emojis and labels
- `<br>` tag after `<summary>` for proper spacing

## Design Decision

### Option 1: Template-Based Implementation (Recommended)

**Debug Section:**
- Modify `DiagnosticContext.GenerateMarkdownSection()` to wrap the entire output in `<details>` tags
- Use `<summary>🐛 Debug Information</summary>` (with non-breaking space)
- Include `<br>` after the summary tag
- The `<details>` block is collapsed by default (no `open` attribute)

**No-Changes Summary:**
- Modify `_summary.sbn` template to check `summary.total == 0`
- If true, render `No changes` instead of the summary table
- Modify `default.sbn` template to conditionally render the Resource Changes section only when `module_changes.size > 0`
- This avoids redundant "No changes" messages (summary already shows it)

**Pros:**
- Leverages existing architecture patterns
- No changes to core rendering logic
- Debug enhancement is self-contained in `DiagnosticContext`
- Template changes are minimal and readable
- Aligns with existing style guide patterns (details blocks already used for resources)

**Cons:**
- Debug section formatting is hardcoded in C# rather than template-driven
- Requires coordination between template changes (summary and default)

### Option 2: Template-Driven Debug Section

**Debug Section:**
- Add `DiagnosticSection` property to `ReportModel` containing the markdown from `GenerateMarkdownSection()`
- Include debug section in the main template with conditional rendering and details wrapper
- Move collapsibility logic into templates

**Pros:**
- More consistent with template-first approach
- Debug presentation fully customizable via templates

**Cons:**
- Adds complexity to `ReportModel` for a debug-only feature
- Debug content is not always present (optional based on `--debug` flag)
- Templates would need null-checking for the diagnostic section
- More invasive changes to rendering pipeline

### Option 3: Post-Processing Markdown Transformation

**Debug Section:**
- Use regex to find and wrap `## Debug Information` sections in the final markdown output
- Apply transformation in `ProgramEntry.cs` after debug section is appended

**Pros:**
- No changes to `DiagnosticContext` internals
- Could be applied to other sections generically

**Cons:**
- Fragile regex-based parsing of markdown structure
- Harder to maintain and test
- Violates separation of concerns (presentation logic in orchestration layer)
- Risk of breaking valid markdown content

## Decision

**Choose Option 1: Template-Based Implementation**

This option provides the best balance of:
- **Minimal invasiveness**: Changes are localized to specific components
- **Architectural alignment**: Uses existing patterns (details blocks, template conditions)
- **Maintainability**: Clear separation between debug formatting (C#) and report formatting (templates)
- **Style guide compliance**: Follows established patterns for collapsible sections

## Implementation Notes

### 1. Collapsible Debug Section

**File**: `src/Oocx.TfPlan2Md/Diagnostics/DiagnosticContext.cs`

**Modification Location**: `GenerateMarkdownSection()` method (line 194)

**Changes:**
1. Wrap entire output in `<details>` tags
2. Replace `## Debug Information` heading with `<summary>🐛 Debug Information</summary>` (using non-breaking space `\u00A0`)
3. Add `<br>` tag after the `<summary>` line for proper spacing
4. Preserve all subsection headings (`### Principal Mapping`, `### Template Resolution`)
5. Close with `</details>` tag

**Example Output:**
```markdown
<details>
<summary>🐛 Debug Information</summary>
<br>

### Principal Mapping

Principal Mapping: Loaded successfully from 'principals.json'
- Found 5 users, 3 groups, 2 service principals

### Template Resolution

- `azurerm_virtual_network`: Built-in resource-specific template: azurerm/virtual_network.sbn
- `azurerm_subnet`: Default template

</details>
```

**Edge Cases:**
- When no diagnostics are collected, the message "No diagnostics collected." should still appear inside the details block
- The `<details>` tag should NOT have the `open` attribute (collapsed by default)

### 2. No-Changes Summary Format

**Files:**
- `src/Oocx.TfPlan2Md/MarkdownGeneration/Templates/_summary.sbn`
- `src/Oocx.TfPlan2Md/MarkdownGeneration/Templates/default.sbn`

**Template Logic:**

**In `_summary.sbn`:**
```scriban
## Summary

{{ if summary.total == 0 }}
No changes
{{ else }}
| Action | Count | Resource Types |
| -------- | ------- | ---------------- |
| ➕ Add | {{ summary.to_add.count }} | ... |
| 🔄 Change | {{ summary.to_change.count }} | ... |
| ♻️ Replace | {{ summary.to_replace.count }} | ... |
| ❌ Destroy | {{ summary.to_destroy.count }} | ... |
| **Total** | **{{ summary.total }}** | |
{{ end }}
```

**In `default.sbn`:**
```scriban
{{ include "_header.sbn" }}

{{ include "_summary.sbn" }}

{{ include "_code_analysis_summary.sbn" }}

{{ if module_changes.size > 0 }}
## Resource Changes

{{ for module in module_changes }}
...
{{ end }}
{{ end }}
```

**Key Points:**
- The conditional check `if summary.total == 0` is the authoritative "no changes" detection
- `module_changes.size == 0` may also be true for no-changes plans (empty list)
- When summary shows "No changes", Resource Changes section should not render at all (avoid redundancy)
- Code Analysis Summary section should still render if present (orthogonal feature)

### 3. Summary-Only Template

**File**: `src/Oocx.TfPlan2Md/MarkdownGeneration/Templates/summary.sbn`

**Impact**: This template also uses `_summary.sbn` partial, so the no-changes logic will automatically apply when users use `--template summary`.

### 4. Detection Logic

**No-changes condition**: `summary.total == 0`

This is calculated as:
```
summary.total = summary.to_add.count + summary.to_change.count + 
                summary.to_destroy.count + summary.to_replace.count
```

The `SummaryModel.Total` property (set by `ReportModelBuilder.Summaries.cs`) already provides this value.

**Why not check individual counts?**
- `summary.total` is the single source of truth
- Already computed and exposed in the model
- Simpler template logic
- Consistent with summary table display

### 5. Testing Considerations

**Test Files to Update:**
- Tests that verify debug output format (need to expect `<details>` wrapper)
- Tests for no-changes plans (verify "No changes" text instead of empty table)
- Snapshot tests for default template output

**Test Scenarios:**
- Debug section with diagnostics (verify collapsible format)
- Debug section without diagnostics (verify "No diagnostics collected" is inside details block)
- Plan with zero changes (verify summary shows "No changes", Resource Changes section omitted)
- Plan with changes (verify summary table renders normally, Resource Changes section appears)
- Summary-only template with no changes (verify "No changes" appears)

### 6. Style Guide Updates

**File**: `docs/report-style-guide.md`

Add documentation for:
- Collapsible debug section structure and usage
- No-changes summary format and when it applies
- Relationship between Summary and Resource Changes sections in no-changes scenarios

## Consequences

### Positive
- **Cleaner reports**: Debug information no longer dominates the visible output
- **Professional appearance**: No-changes plans show a simple, clear message instead of empty tables
- **Reduced redundancy**: Single "No changes" message instead of two separate sections
- **Backward compatible**: Collapsing debug section doesn't change content, only presentation
- **Template consistency**: No-changes logic uses existing template conditional patterns
- **Accessibility**: Debug information remains fully accessible when needed

### Negative
- **Breaking change for tests**: Debug output format changes require test updates
- **Markdown rendering dependency**: `<details>` tag support required (both GitHub and Azure DevOps support it)
- **Template coupling**: Changes to `_summary.sbn` affect both `default.sbn` and `summary.sbn` templates

### Risks to Monitor
- **Markdown compatibility**: Verify `<details>` rendering in both GitHub and Azure DevOps PR comments (should be fine; already used for resources)
- **Template maintenance**: Ensure `_summary.sbn` changes don't break custom templates that include it
- **Edge cases**: Verify behavior when code analysis findings exist but no resource changes (should show "No changes" in summary, then findings in separate section)

## Alignment with Architecture

This design aligns with existing tfplan2md architecture:

- **Template-Based Rendering** (ADR-001): Uses Scriban templates for presentation logic
- **Report Style Guide**: Follows established patterns for collapsible sections and formatting
- **Component Boundaries**: Debug formatting in `Diagnostics/`, template logic in `MarkdownGeneration/Templates/`
- **Optional Features**: Debug section only rendered when `--debug` flag is used
- **Platform Compatibility**: Both GitHub and Azure DevOps support `<details>` tags (already used for resources)
